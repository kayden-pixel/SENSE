# Security

Do not post credentials, training samples, raw camera frames or private recordings in public issues. For a vulnerability, use GitHub private vulnerability reporting on the repository when enabled; otherwise contact the maintainer privately through their GitHub profile before disclosing details.

Tokens are random 256-bit values. The server stores only token hashes, passwords use PBKDF2-SHA256 with per-account salt and 600,000 iterations (legacy 210,000-iteration hashes are upgraded after successful login), and tokens expire after 30 days. Android session credentials and mouth templates are sealed by Android Keystore AES-GCM. Android backup is disabled. Camera and microphone data are not logged. App transport is HTTPS/WSS and voice media uses WebRTC encryption; server operators can access media at the SFU, so this is not a claim of end-to-end encryption.

Rooms require invitation, membership and continuing friendship with the host. LiveKit grants expire quickly, authorize microphone-only publication and are generated on the server. Removing/blocking users preserves block ownership, revokes shared membership and queues exact room/identity ejections durably. Unrelated rooms are untouched. Failed ejections retry every minute; the API reports 503 while pending. Expired rooms are queued for ejection within one minute. Initial API-issued join grants expire after at most two minutes and are capped at the SENSE session expiry. LiveKit can independently refresh tokens during a connection, so this initial TTL does not bound every cached token or end an active call. On self-hosted LiveKit, removing a participant does not guarantee revocation of every previously issued join token: a malicious client may replay a still-valid token. Immediate, strict media revocation remains a deployment/integration blocker and must be validated on the chosen LiveKit service. See the upstream [token lifecycle and revocation reference](https://docs.livekit.io/frontends/reference/tokens-grants/#token-lifecycle). Distribute invitations only to trusted friends. Rate limits are per-IP/per-user for this single-process service; multi-instance deployments must share a limiter and database.

Rotate RADAR_SECRET only with an intentional nearby-identifier reset. Keep LiveKit API secrets out of APKs and Git. TLS termination, request limits, storage encryption, backups, log retention and media retention are operator responsibilities. API has bounded JSON bodies, clip size/hash checks, parameterized SQL and no client-selected storage paths.

Known beta limits: no lost-key recovery/MFA/account-deletion UI, local profile metadata is app-sandboxed rather than field-encrypted, capture clips are ordinary private app files, privacy does not verify owner identity or gaze, hardware flows need physical-device validation. Do not use Veil as a security boundary or Silent for high-risk commands.

Blocked records disclose no live presence, ranging availability or avatar updates. Nearby identifiers rotate every five minutes; a previously accepted friend may retain an identifier until that rotation. Precise ranging negotiation requires a recent BLE observation and current accepted-friend authorization, but BLE identifiers are discovery hints, not cryptographic proof of a person’s location. Signal relay/spoofing is possible. Stereo panning requires a stereo-capable output; Bluetooth call routes may be mono.

Usernames are case-insensitive invite addresses, not authentication secrets. New phones generate 256-bit recovery credentials locally, sealed with Android Keystore and bound to their HTTPS origin. Existing ID/password accounts remain supported. Only the operator can provision an owner through server-side OWNER_ACCOUNT or OWNER_ACCOUNT_FILE configuration containing a salted PBKDF2 hash. Owner recovery credentials must stay out of source control, build settings and shared APKs. Recovery keys give full identity access; keep them private. The backend does not automatically grant the first visitor an owner role.

Production packaging uses only the official public URL in config/production.properties; release ignores debug/custom endpoint preferences. Signing credentials are environment-only. The release gate requires live API/media readiness and private signing; CI cannot publish a developer APK as a production release. Readiness actively authenticates against LiveKit, coalesces requests, and exposes only service booleans. Voice-token authorization is rechecked after the readiness network call, so logout or removed membership cannot be revived by a delayed check.
